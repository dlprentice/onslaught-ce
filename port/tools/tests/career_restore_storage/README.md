This suite exercises the production storage entry points in `ce_career_restore.h` on newly generated disposable profiles. It does not enable Restore in a menu. Run `python3 -B port/tools/tests/career_restore_storage/run.py` from the repository with the usual port toolchain configured. It accepts no profile, game-data or backup path. All generated inputs and receipts remain in ignored `local-data/`.

The Linux backend supports a local, accessible ASCII career namespace and the current career format accepted by the ordinary preview reader. It refuses the whole operation if any career is ambiguous, linked, unsupported or cannot be captured. The complete set contains every effective career from the user and original-game folders, with normal user precedence, plus the user's `defaultoptions.bea` when present. A shadowed original remains read-only and is rechecked. Missing options are not manufactured; other configuration files are not claimed as backed up.

`CeCareerBackupAll` publishes the checked external set. `CeCareerRestoreAsNew` first rereads the selected preview identity, then makes that full set in the same operation. The read-only `CeCareerRestoreStamp` binds the preview identity to the set directory, manifest and member identities at selection; the supplied stamp is required and rechecked. Replacing a member with identical bytes is still a change. It stages the selected bytes anonymously beside the destination, checks them, and publishes an intact new file without replacement. Ordinary save methods and their dispatch remain unchanged. The actual memory-card reader, lister and writer are exercised separately against the result.

`CeCareerRestoreSuggest` proposes a readable ordinary filename such as `Amber restored.bes`, then `Amber restored 2.bes`. A copy of an already restored source advances that sequence. The basename fits the native 31-unit limit; long names are shortened for the proposal. This call is read-only: it neither reserves a name nor approves filename-dependent game behavior. After the game thread compares the exact source and proposed names, the caller freezes the approved pair and passes `targetName` at confirmation. The mandatory `namePermitted` callback checks that pair. Missing approval, unsafe shortening or a later name clash refuses the operation; the backend never silently chooses another target during confirmation. No metadata, display alias or save-format change is introduced. The result returns exactly the confirmed filename.

A readable filename contains letters, so a process that ignores the new operation lock can race by choosing another spelling of the same name. The backend scans both locations for current aliases, publishes the exact target without replacement, and checks the whole namespace after publication. A late incompatible alias produces `Uncertain`; both files are preserved for inspection. This is not an exclusive cross-process reservation of every case variant. Actual ordinary memory-card listing, reopening, duplicate admission and resaving are separately exercised with the readable result and a maximal-length proposal.

The operation lock serializes these new APIs only. It is not a promise that older games, the Companion or an external editor obey it. A late outside change, including a case-only alias, `.BES` insertion or original-folder write, can still occur across the final check. A detected post-publication change returns `Uncertain`, retains the new file and the backup, and never rolls another writer back. The caller must not retry automatically. A cancelled operation can leave a completed full backup; a killed backup copy can leave a private `.pending-` directory outside the profile. The anonymous career stage leaves no visible empty slot. The tests cover process interruption, not power-loss recovery.

The caller must hold and recheck the front-end, open-card, main-thread and excluded-session/replay authority through `permitted`; the API does not infer it from filesystem paths. `cancelled` is consulted before publication. No current page supplies this authority or calls the restore API. This Linux suite cross-compiles the Windows custody backend with strict warnings (`windows_closed.cpp`) without executing it; Windows custody execution under Wine lives in `port/tools/ce_career_restore_windows_tests.py`. Independent safety review and all player-facing M5 conditions remain necessary before integration or UI enablement.

The suite intentionally depends on the authored `restore_custody/preview.cpp` helper introduced by prerequisite commit `02483010`; carry that test-only prerequisite before this backend series. The ordinary product backend does not depend on a test source. The production Linux storage fixture is built and run as ELF32 with strict warnings enabled; the independent preview generator remains a host-side test tool.

Discovery in the restore backend and naming proposal stops after 2,048 total entries per save directory, including irrelevant entries; the existing ordinary preview reader separately caps its scan at 8,192. These work limits, the member/count limits and local-storage checks are not a guarantee against a filesystem syscall stalling. The fixture records observed selection, suggestion and publication durations; there is no timeout that kills a writer. The game thread must render a working state before a synchronous publication call and retain exclusive native save ownership until it returns.
